# DriveSafe Demonstration Script

Use this as a spoken script during a live demo.
Estimated runtime: 8 to 12 minutes.

## 1) Opening (15-20 seconds)

Hello everyone. This is DriveSafe, a real-time pedestrian safety assistant.
In this demo, I will show what the driver sees on screen, how alerts are triggered, how controls work, and how events are archived for review.

## 2) Start With Bounding Boxes (1.5-2 minutes)

As requested, let us begin with the bounding boxes.

What you are seeing:
- Each detected object is highlighted with a corner-style box.
- Pedestrians and crosswalks are tracked continuously.
- Each object gets a label with class, track ID, and estimated distance in meters.
- Example labels look like PED #4 6.2m or CW #1 8.5m.

What matters operationally:
- The center path zone is the driving path. Only pedestrians in this zone escalate driving alerts.
- In-path pedestrians are visually emphasized so the driver can separate critical vs non-critical detections quickly.
- Color coding communicates risk immediately:
- Green means safe.
- Amber means warning.
- Red means danger.

What to say while moving scene content:
- If a pedestrian is outside the lane path, it is still detected and shown, but treated differently for hazard escalation.
- As an object gets closer, distance values update frame by frame.
- The system keeps identity over time using tracking IDs, even as the object moves.

## 3) Splash Screen To Live View (1 minute)

Now I will restart so you can see the startup experience.

Narration during splash:
- First, DriveSafe shows a splash screen with the project branding and loading status.
- You will see staged startup messages such as loading configuration, initializing model, setting up camera, and starting DriveSafe.
- This gives the user clear feedback that the model and pipeline are initializing.

Narration when main window appears:
- After initialization, the app opens in full-screen live mode.
- The central area is the live camera feed.
- The top includes the control toolbar.
- The bottom status bar shows current FPS, processing latency in milliseconds, counts of pedestrians and crosswalks, and system mode indicators.

## 4) Toolbar Walkthrough (2-3 minutes)

Now I will explain each toolbar control from left to right.

1. Burger menu (Menu)
- This opens the main menu.
- The key item here is Archive, where all saved recordings and automatic clips are listed.

2. Record button
- This starts and stops manual recording of the current live feed.
- When active, recording status appears clearly and the session is written to the recordings folder.
- Use this for operator-controlled capture, such as test runs or user reports.

3. Mute Alerts
- Toggles voice alerts on or off.
- Visual warnings continue, but audio guidance is silenced when muted.
- Useful for quiet environments, lab testing, or replay sessions.

4. Info Panel
- Toggles an overlay panel with system information and control hints.
- It helps operators check model and runtime parameters quickly during validation.

5. Quit
- Safely exits the app and stops the processing thread cleanly.

Keyboard shortcuts to mention live:
- R toggles Record.
- M toggles Mute.
- I toggles Info Panel.
- Q quits.
- Escape exits full-screen first, then can close.

## 5) Archive Section In Depth (3-4 minutes)

Now let us open Archive from the menu.

What Archive contains:
- Manual recordings from the Record button.
- Automatic safety clips generated by event triggers.

How automatic clips are recorded:
- DriveSafe continuously keeps a rolling pre-event frame buffer.
- When risk reaches the configured trigger level, clip capture is triggered.
- The saved clip includes:
- Frames before the event (pre-seconds).
- Frames after the event (post-seconds).
- This creates full context, not just the incident instant.

Default event-capture behavior in this project:
- Pre-event buffer is 3.0 seconds.
- Post-event capture is 3.0 seconds.
- Trigger level is configured to warning (so warning and danger can produce clips).
- Cooldown is 10 seconds to avoid excessive duplicate clips.

Important implementation detail to explain:
- If repeated triggers happen during an active clip window, the system extends the post-event section instead of creating many tiny files.
- That produces one meaningful event clip for continuous risk intervals.

How files are named and classified:
- Manual: drivesafe_YYYYMMDD_HHMMSS.avi
- Auto warning: clip_warning_YYYYMMDD_HHMMSS.avi
- Auto danger: clip_danger_YYYYMMDD_HHMMSS.avi

What the Archive table shows:
- Filename
- Type (Recording, Clip Warning, Clip Danger)
- Date/time
- Duration (calculated from frame count and FPS)
- File size

Archive tools to demonstrate:
- Filter buttons: All, Recordings, Clips Warning, Clips Danger.
- Double-click or Play to open in media player.
- Delete with confirmation prompt.
- Refresh to reload folder contents.

Operational value statement:
- Archive is not just storage.
- It is an evidence and review layer for incident analysis, model tuning, and operator training.

## 6) Closing (20-30 seconds)

To summarize:
- DriveSafe detects and tracks pedestrians and crosswalks in real time.
- It estimates distance, evaluates risk level, and provides visual plus voice guidance.
- The toolbar gives immediate control over recording, audio, and UI overlays.
- The Archive preserves both manual sessions and automatic event clips with before-and-after context.

Thank you. I can now run a short live scenario with one warning event and one danger event so you can see the full detection to archive workflow end to end.
